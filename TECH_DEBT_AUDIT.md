## Architectural mental model

Tauri v2 desktop app: a thin Rust shell (`src-tauri/src/lib.rs`, six `#[tauri::command]`s, no business logic) hosting a React 19 + WebGPU frontend. The frontend has four real layers: `layers/` (pure, tested — `LayerStack`/`History`, the undo/redo and layer-ordering model), `render/` (impure, GPU-only, untested by convention — `Renderer` orchestrates a multi-pass WGSL pipeline per layer, with per-effect modules registered in `render/effects/registry.ts`), `mask/` (pure, tested — `MaskPainter`, a CPU-side brush raster), and `ui/`+`components/` (a small hand-rolled design system plus the app's actual panels). `App.tsx` is the composition root and owns all cross-cutting state (layers, history, mask-paint mode, GPU refs) — it is intentionally not decomposed further yet.

This branch (`feature/archi-remediation`) is a completed 11-task performance/robustness remediation plan (pipeline caching, GPU-resident masks, rAF-coalesced renders, bounded/refcounted undo history, binary IPC, atomic file writes, CSP) layered on top of that, plus — from *this session specifically* — a live debugging investigation into a recurring renderer OOM crash during mask painting, which produced (a) temporary crash-diagnostic instrumentation and (b) a real fix (dirty-rect-scoped mask texture uploads instead of full-buffer uploads per paint sample). Both (a) and (b) are uncommitted in the working tree as of this audit and are the freshest, least-settled code in the repository — which is exactly where this audit finds real findings, not generic pattern-matching.

## Top 5 — if you fix nothing else, fix these

1. **Remove the temporary crash-diagnostic instrumentation (F001–F004).** This is the single highest-signal finding: it's debug scaffolding that was explicitly self-labeled temporary, added in the last few hours, and its job (root-causing the mask-paint OOM crash) is done. Leaving it in is the textbook way "temporary" debugging code becomes permanent. Concrete diff sketch:
   - Delete `log_diagnostic` from `src-tauri/src/lib.rs` (function + `invoke_handler!` entry).
   - Delete `logDiagnostic` from `src/launch.ts`.
   - In `src/render/gpuContext.ts`: either delete the `device.lost` handler entirely, or keep it but route into `App.tsx`'s existing `error` state instead of `logDiagnostic` — deciding which is a 1-line call, not a redesign.
   - In `src/render/renderer.ts`: delete `diagFrameCount` field and `logFrameDiagnostics` method, and the one call site in `runPipeline`.
   - Run `npx tsc --noEmit && npm run test && cd src-tauri && cargo check` after, per this project's own verification convention.

2. **Extract and test the dirty-rect upload math (F005).** This landed to fix a real, reproduced-4-times production crash. Right now the only "test" it has is a human manually painting in the live app. Given the offset/stride arithmetic is exactly the kind of thing that's easy to get subtly wrong at an image edge (and *was* already getting subtle treatment via `Math.max(0, ...)`/`Math.min(width-1, ...)` clamping in `MaskPainter.paintStroke`), it deserves the same test rigor Task 1/2/4/5 of the remediation plan already established for this codebase's other pure GPU-adjacent logic.

3. **Decide Dialog/Progress's fate (F009/F010), don't leave them in limbo.** Either they're near-term roadmap (export progress, confirmation dialogs) and should get a tracking note somewhere discoverable, or the plan changed and they're dead code. Right now there's no way for a future reader to tell the difference without archaeology through old planning docs — which is exactly the kind of ambiguity a codebase this young shouldn't already have.

4. **Collapse the 4 `writeTexture` call sites (F006) while F005's extraction is already in progress** — same file, same function family, and doing it in the same pass avoids a second review cycle touching the same lines.

5. **Batch the 8 clippy warnings (F013–F020) into one `cargo clippy --fix` + manual pass commit.** All Low severity, all Small effort, none touch logic — the only reason to bundle them is that a `cargo clippy --fix` diff reviews faster as one commit than as noise scattered across unrelated future commits.

## Things that look bad but are actually fine

- **`scripts/cdp-console.mjs` flagged "unused" by `knip`.** It's never `import`ed by any TS/JS module — `knip`'s static analysis can't see that `scripts/monitor.ps1` spawns it as a subprocess (`Start-Process -FilePath node.exe -ArgumentList cdp-console.mjs`). This is a real, working part of the dev-debugging tooling (used extensively this very session), just invisible to import-graph tooling. Leave it.
- **No unit tests for `render/renderer.ts`, `render/gpuContext.ts`, or any `render/effects/*.ts` file.** Looks like a coverage hole at first glance (11 files with no matching test). It's a deliberate, explicitly documented project convention (`CLAUDE.md`: "le rendu GPU se vérifie visuellement, pas unitairement" — GPU rendering is verified visually, not with unit tests, since there's no WebGPU implementation available in the Vitest/Node test environment). The project's actual discipline shows in what *is* extracted and tested: every piece of pure logic that COULD be tested without a real GPU already is (`shaderCompose.ts`, `maskResidency.ts`, `limits.ts`, `effects/validate.ts`, `frameScheduler.ts`). F005 is flagged specifically because it's new pure logic that broke this pattern, not because untested GPU code in general is a problem here.
- **`EffectParam`/`EffectPass` (`render/effects/types.ts`) and `ButtonVariant`/`ButtonSize`/`IconButtonVariant`/`SelectOption` flagged as "unused exported types" by `knip`.** These are legitimate public contract types for a module registry pattern (`EffectModule.params: EffectParam[]`) and a small hand-rolled design system (prop types consumers pass string literals into, so TS's structural typing means the type name itself is rarely imported by name even though the contract is very much alive and load-bearing). Exporting them is correct API design, not dead code.
- **Rust: zero `.unwrap()`/`.expect()` outside the test module.** This looked worth double-checking given how common unwrap-panics are in early-stage Rust/Tauri code — verified via direct `grep`, genuinely clean. The one `clippy::map_unwrap_or` hit (F017) is a style suggestion on a `Result`-mapping chain, not a panic risk.
- **`src/App.tsx`'s 307-line god-object shape.** Already covered as F008 above — flagged here again only to be explicit that this audit is *not* independently discovering new architectural debt; it's confirming a finding this project's own prior audit already made and deliberately deferred with a named trigger. Re-flagging it as urgent would contradict that prior, reasoned decision.
